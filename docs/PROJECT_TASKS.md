## T02

### 计算前核验适用条件和参数

#### 现象

原版已上 8 节案例算出 1920 元，但该轮未产生 function 消息，也未提及同页第四条提前解约 30% 违约金。明确要求调用后，MCP 工具真实返回 1920 元。
已上 13 节时，模型本次正确拒退；不能将其写成已观察到的失败。但 calculate_refund 本身不检查“超过 12 节不支持退费”，应测试整体流程边界。

#### 建议任务（待认领）

- 显式记录资格／限制、相关条款、参数值及 evidence_id。
- 条件满足且参数齐全后调用现有确定性计算器；记录实际调用而非只看回答是否含公式。
- 适用条款不明确、违约金是否叠加不明确时，输出条件化测算和澄清问题，不能擅定唯一净退款。
- 将工具单元验收与端到端参数／条款选择验收分开。

#### 验收案例

8 节、12 节、13 节；缺实付金额；原价与优惠价并存；手续费基数变化；违约金是否叠加待确认。
超过 12 节不得仅套公式给出可退款结论。1920 仅是第三条公式的结果，不自动代表完整合同的最终净退款。

认领后独立分支开发；本任务 不预先指定法律解释。

## T03

### 沙盘缺失评分处理

#### 已确认的确定性问题

vam_sandbox/pipeline.py 的 normalize_evaluations 对缺失叶子填入 benefit/risk/cost/opportunity_cost=5、probability=0.5；_score 将其算为 50 分。
2026-11-14 已在本地直接调用这两个纯处理函数验证：当 B1 缺失、B2 的 benefit=4,risk=6,probability=0.4,cost=6,opportunity_cost=6 时，B1 得 50，B2 得 40，缺失评估可能被排在有效评估之前。
前一次网页运行的最优分支也出现同样默认值且理由为空，但当时没有完整核对 raw_eval；不要把其具体触发原因写成已确认。

#### 建议任务（待认领）

- 缺失／非法评分保留 missing 或 invalid 状态，不伪装为模型有效评分。
- 未评估叶子不参与最优排序；全缺失时显示“无法推荐”。
- 可配置有上限的补评，记录补评次数、原始输出及额外用量。
- UI 区分有效评分、缺失、补评结果。

#### 验收

覆盖缺失叶子、全部缺失、错误 leaf_id、重复 ID、非法值；缺失分支不能胜过有效分支。保留原始评估，不能静默补分。
这是数据完整性任务，不证明模型的概率或现实建议经过校准。

## R01

### 证据预算与可靠性实验

#### 研究问题

合同证据或工具输出压缩后，保留哪些条件才能支持正确判断？允许有限重查后，累计调用与 token 是否仍减少？
这是拟开展的扩展实验，不是现有能力，也不预设某种压缩一定胜出。

#### 已有基础

agent-budget-lab（https://github.com/os-till-go/agent-budget-lab）已提供真实模型诊断、完整／错误过滤／条件保留／无日志四组、有限重查和轨迹记录。当前 1B 模型连完整日志的成对任务也不稳定，现有结果不能证明压缩方法优劣。

#### 计划

- 独立 research/evidence-budget 分支，只通过适配器接现有 Assistant，不直接改 main 或重写平台。
- 先用本机已安装的 qwen2.5:7b 检查完整日志能否支持成对任务；若仍失败，先检查理解与协议，暂停算法排名。
- 再把实验迁移到短合同／条款片段：适用对象、超过 12 节等例外、手续费基数、相关条款；增加无日志及关键条件遮蔽对照。
- 给相同查询权限和上限，记录实际上下文、重查、最终正确性及总用量。
- 手工提供的证据位置用于隔离实验时，明确标作人工定位参照，不当作自动检索成果；后续再接自动定位。
- 用简单固定策略作基线，再讨论自适应分配预算；不同时扩大到 VLA、模型训练或完整多 Agent 系统。

#### 交付与停止条件

计划、适配器、可复跑结果和失败分析；保留独立测试。若基线不能理解任务，或差异只来自泄漏／人为标记，调整协议而非追加有利案例。
基础问题通过本清单 T01–T05 认领，本实验不等待所有基础功能完成；独立运行所需最小适配先在分支内实现。

## C01

### 连接器与 Git 的协作访问

#### 本次核验（2026-11-14）

- 当前连接器的账号已核对为 `os-till-go`，但读取本仓库元数据返回 404。
- 使用本机 Git Credential Manager 的现有凭据，`/user` 同样确认为 `os-till-go`，读取同一私有仓库和 issues 成功；权限为 `pull=true, push=true, admin=false`。
- 当前连接器可见的安装账户未包含 `peng-fang`。这提示当前连接没有目标账户的安装访问路径，但不能据此断言所有者从未安装过 App。
- 因此本地 Git/API 可以继续协作；连接器还需独立完成安装/授权核对。此次没有修改仓库可见性或任何 App 授权。

#### 待核对事项（协作流程任务）

1. 仓库所有者在 GitHub Settings → Applications → Installed GitHub Apps，确认与所用客户端对应的**同一款 App**是否已安装，并在 Configure 中包含本仓库。只选择需要的仓库即可。
2. 使用者核对连接器账号、已接受的协作邀请、更新的权限授权，并刷新连接/仓库列表。
3. 所有者已经授权而仍 404 时，继续核对是否不同 App、用户授权不完整、凭据过期，或组织策略（若为组织仓库）；不能仅凭网页可见就判断程序凭据也可见。
4. 写明备用工作流：各成员用自己的本机 Git/SSH/凭据管理器访问；issue/PR 可使用相同身份的已授权 API。无需共享个人 token 或将仓库公开。

#### 验收

- 同一个 Agent 连接器可以读取本仓库 README 与 issue，作为连接器恢复的标准。
- 若连接器未恢复，本机 Git/API 工作流仍可 clone/pull、独立分支推送与管理 issue/PR。
- 说明认证不足时 GitHub 可能以 404 隐藏私有资源，而不是只返回 403。

参考：[GitHub REST 认证排错](https://docs.github.com/en/rest/using-the-rest-api/troubleshooting-the-rest-api#404-not-found-for-an-existing-resource)、[GitHub App 安装与授权](https://docs.github.com/en/apps/using-github-apps/installing-a-github-app-from-a-third-party)。
