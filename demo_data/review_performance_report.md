# 合同风险审查性能评估

测试日期：2026-11-16  
测试合同：`output/contracts/hk_employment_contract.pdf`（香港雇佣合同，2 页，16 条条款）  
法域：中国香港；合同类型：自动识别  
环境：本地 Ollama `qwen2.5:7b` + Tavily + 本地规则/条文库

## 0. 第二轮优化后（最新）

在原有缓存、SSE、预加载、并发网页检索基础上，又做了：

- 高置信度自动分类跳过分类 LLM；
- Judge 只审 high/medium，low 走确定性复核；
- Tavily 默认 basic，失败再 advanced；
- Judge 默认压缩输入；
- 前端支持取消；
- 已知类型低风险不联网，未知类型低风险最多补 2 条。

| 场景 | 优化前 | 优化后 | 变化 |
| --- | ---: | ---: | ---: |
| 完整 LLM | 146.56s | 99.78s | -32% |
| 快速模式（联网并发） | 19.69s（首次） | 5.80s | 约 -70% |
| 分类阶段 | 6.98s | 0.13s | 跳过 LLM |
| 法律检索阶段 | 23.35s | 8.49s | -64% |
| Judge 阶段 | 58.19s | 30.30s | -48% |
| 条款理解 / 风险审查 | 57.90s | 60.86s | 基本不变，仍是主要瓶颈 |

## 0.1 小模型实验

| 配置 | 耗时 | 风险条数 | 结论 |
| --- | ---: | ---: | --- |
| 默认 7B | 99.78s | 11 | 当前默认 |
| `ANALYZE_MODEL=qwen2.5:3b` | 73.63s | 14 | 更快，但风险数明显增加，需人工评估是否误报 |
| `JUDGE_MODEL=qwen2.5:3b` | 103.52s | 12 | 本样例未变快，暂不默认启用 |

## 0.2 当前默认策略

- 分析模型：`qwen2.5:7b`
- Judge：`qwen2.5:7b`
- `ANALYZE_MODEL` / `JUDGE_MODEL` 保留为可配置项，不默认使用 3B。

## 0.3 Judge 模型 A/B（同一批 7 条风险）

| Judge | 耗时 | judgments | 状态 |
| --- | ---: | ---: | --- |
| `qwen2.5:7b` | 31.2s | 7 | 全部 needs_review |
| `qwen2.5:3b` | 15.5s | 7 | 全部 needs_review |

结论：只看 Judge 本身，3B 约快 2 倍；但样本中两者都判 needs_review，语义质量差异仍需更大样本评估。

之前完整流程 3B Judge 总耗时 103.52s，比 7B 的 99.78s 慢，原因是分析阶段本身波动（67.37s vs 60.86s），不是 Judge 变慢。

## 0.4 Judge A/B：准确性

同一批风险分别用 7B / 3B Judge：

| 案例 | 7B | 3B |
| --- | --- | --- |
| 内地租赁（8 条） | 6 supported / 2 rejected | 8 条全部 needs_review |
| 内地消费（5 条） | 3 supported / 2 needs_review | 仅返回 4 条，全部 needs_review |
| 香港劳动（7 条） | 全部 needs_review | 全部 needs_review |

结论：3B Judge 速度约快 2 倍，但在“有可核验本地法条”的场景明显更保守，容易把 supported 降成 needs_review，不能单独作为主 Judge。

## 0.5 混合 Judge（当前启用）

策略：

```text
有 verified 本地法律依据 → 7B
没有 verified 法律依据     → 3B 快模型
最终仍由确定性 guard 强制 needs_review
```

实测香港雇佣合同（全部无核验依据）：

```text
完整流程：69.1s
分析：49.7s
Judge：19.4s
风险：12 条
warnings：[]
```

对比全 7B 的约 99.8s，混合模式约省 30s；有本地法条的场景仍使用 7B，避免 3B 把 supported 误降。

配置：

```env
JUDGE_FAST_MODEL=qwen2.5:3b
```

## 3. 结论

### 有效优化

1. **整份结果缓存效果最大**：同一合同第二次审查从 19.69s 降到 0.05s。
2. **快速模式显著缩短等待**：本样例从 146.56s 降到 19.69s，但风险条数从 11 降到 7，属于质量与速度的取舍。
3. **并发网页检索在理想情况下有效**：串行 33.98s，首次并发 19.69s，约减少 42%。
4. **SSE 不缩短后端时间**，但让用户看到阶段进度，避免误以为卡死。
5. **预加载模型**降低首次调用中的模型加载等待；本次测试时模型已预热，未单独量化。

### 不足

1. **LLM 仍是主要瓶颈**：完整模式 146.56s 中，约 123s 花在分类、分析和 Judge。
2. **并发网页检索不稳定**：重复测试出现 53.79s、57.08s，说明 Tavily 限流/网络波动会抵消并发收益。
3. **快速模式质量下降**：风险条数 7 vs 11，缺少模型语义判断。
4. **缓存只解决重复审查**：首次审查、文件改动、法域/类型/模式变化都会 miss。
5. **Judge 小模型未默认启用**：`gemma3:1b` 实测不完全遵守 JSON schema，可能把状态写成 `supported|needs_review|rejected`。
6. **低风险跳过联网**会减少搜索量，但低风险如果本地也没有依据，会更多落到“待人工复核”。

## 4. 建议

- 日常快速扫描用「快速模式」；正式交付用完整 LLM。
- 保留整份结果缓存，演示/重复审查收益最大。
- 若 Tavily 经常波动，优先保证缓存命中，其次考虑降低 workers 或增加超时/重试。
- 不要把 `gemma3:1b` 直接作为默认 Judge；如需更小模型，优先测试 `qwen2.5:3b` 等更遵守 JSON 的模型。
- 在页面上继续保留阶段进度和已等待时间；这不会变快，但能显著改善等待体验。
