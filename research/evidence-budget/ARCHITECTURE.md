# 我们在这个底座上研究什么

日期：2026-11-14。源码基线 `88c7bb5`；只做计划，不修改共享 main，不实现或承诺尚不存在的模块。

## 三层需要分清

1. **Qwen-Agent 上游框架**：模型抽象、工具注册与调用循环、文件记忆/检索、Gradio UI。它支持开发不同 Agent 应用，并非只给合同设计；也不等同于已搭好的 nanobot 个人助理产品。
2. **本项目合同应用**：`examples/assistant_contract_local.py` 配置 Assistant、模型、业务提示和三个 MCP 计算器。抽条款、核对条件、判断矛盾，主要依靠同一模型执行提示，尚未分成独立结构化流水线。
3. **本项目沙盘应用**：`vam_sandbox/pipeline.py` 两阶段模型调用（推演、评估），再由 Python 归一化与排序。当前主要入口接文本；合同 UI 到沙盘是页面链接，没有自动传递已验证合同证据的链路。

“读文档套 Agent”抓住了合同应用复用框架的事实，但遗漏了实际工具循环与计算器；“平台已经具备可靠条款抽取和矛盾判断”又会高估当前实现。我们要验证证据、动作与结果之间的关系。

## 三条可选研究路线

| 路线 | 可检验问题 | 最小对照 | 与当前代码的关系 | 优先级 |
|---|---|---|---|---|
| A. 关键条件保留与按需重查 | 少给证据后，限制/例外/金额基数是否丢失？补查后的总开销是否仍小？ | 完整、简单过滤、条件保留、无证据；再打开相同上限的重查 | 复用 agent-budget-lab 的协议与轨迹思路，通过 knowledge 和自定义证据工具接 Assistant | 第一选择，承接已有 demo |
| B. 有限预算下选择下一步 | 有限调用应花在查例外、读相邻条款、计算还是请求澄清？ | 固定流程、固定轮转、基于当前缺项选动作；相同工具和预算 | 在 A 的可靠任务与工具接口成熟后扩展；借鉴 AgentPilot 的预算决策思想 | 第二阶段，不先训练策略模型 |
| C. 条件变化后选择性重算 | 用户把已上课时从 8 改为 13，或更新一个条款，哪些旧结论必须失效？ | 全量重做、简单复用、依据条件依赖重算 | 保存事实/证据版本与计算参数，用既有计算器检查旧答案是否残留 | 备选；若当前资料太短、压缩价值不足，可转此路线 |

路线 B 在单任务中挑下一步只证明预算策略效果；若声称“学会了改进”，还需跨任务经验和新任务评价。路线 C 可对应课堂中途追加需求与复用工作的讨论。

## 最关键的接入事实

### 1. 长文本主要在知识上下文，不在计算器返回里

[`Assistant._prepend_knowledge_prompt`](../../qwen_agent/agents/assistant.py) 先调用 Memory 获得文件证据，再把它格式化进 system 知识区；[`FnCallAgent._run`](../../qwen_agent/agents/fncall_agent.py) 随后执行模型—工具循环。

三个 MCP 计算器返回较短的数字、字段和公式。不能只在 `_call_tool` 后压缩这些 JSON，就以为已经控制了 PDF 证据。首轮应明确干预 **RAG 证据送入模型的边界**；工具返回压缩另作条件，不混为一个改动。

### 2. `knowledge=''` 会触发自动检索

Assistant 里是 `if not knowledge: ... self.mem.run(...)`。因此无证据对照不能简单传空字符串，否则又自动检索了文件，实验名称与实际输入不符。

第一版可用显式的外部证据载荷隔离自动检索：按框架支持的 `url/text` 结构传入视图；无证据组传非空的“本组无材料”载荷，且不附上传文件。记录最终传给模型的消息，确认没有其他路径恢复材料。这是待实现和验证的适配设计。

### 3. 重查应是一个真正可调用的工具

拟增加只读的 `read_evidence(evidence_id, start, limit)`，从独立 EvidenceStore 返回原始段落及来源。工具描述、可用动作和查询上限对比较组保持一致；无证据诊断组单独关闭重查。

框架全局默认 `MAX_LLM_CALL_PER_RUN=20`，不是我们的研究预算。实验适配器需要在本分支内显式执行每条任务的调用上限，不能仅在提示中请求模型自觉遵守。

### 4. 精确 token 需要传输层证据

当前兼容模型适配 `qwen_agent/llm/oai.py` 将服务响应转换为 Message，未在返回值中保留 usage；`base.py` 的 OpenAI 兼容输出包装还明确生成了为 0 的 **fake usage**。这些 0 不能作为实际用量。

先记录调用次数与实际可见上下文。精确 token 若要实现，应在模型传输边界读取服务实际 usage，或使用有 usage 记录的受控适配；缺失时记 null。框架日志中的“all tokens: 611”是局部检索/预算统计，不能当作整条任务的输入/输出总账。

### 5. 工具返回正确不等于合同结论正确

`calculate_refund` 只做给定参数的运算，没有“超过 12 节不退”的资格判断；系统提示要求调用计算器，也不能保证模型每次调用。要分别检查适用条件、参数来源、真实 function 消息和最终回答。

## 首轮范围与验收

1. 用已安装模型检查完整证据对照能否稳定随关键条件改变答案。先复用小型诊断，当前阶段不运行已有四道预留题。
2. 从合同自带材料派生少量人工核对的成对任务：改变资格、基数、例外、或是否有足够信息给唯一结论。题目/文件名/选项不泄漏变体。
3. 首先固定相同证据片段研究“看到后如何用”；之后才加入自动检索，区分“没找到”和“找到但用错”。人工位置明确标为人工参照。
4. 现有演示检索记录约 611 token，可能根本没有压缩需求。先测真实上下文构成；若没有足够长且有意义的证据或多轮轨迹，就报告适用边界或转路线 C，而不是只追加无意义噪声。
5. 输出成对正确性、条件遗漏、参数正确性、累计调用/重查、服务报告 token、耗时和原始轨迹。开发与最终保留材料按文档或任务族区分。

第一轮交付是协议、可复跑适配与有效性诊断；没有稳定的完整证据参照时，暂不排名压缩算法，也不承诺提升。
